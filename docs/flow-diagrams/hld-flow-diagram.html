1. System Architecture Overview

The platform is a microservices-based e-commerce system built with Spring Boot 3.4 / Java 21, containerized via Docker Compose, and using Apache Kafka for asynchronous event-driven communication with a Transactional Outbox Pattern for reliability.

3. Core Data Flow — Order Placement (End-to-End)

This is the primary business flow through the system. It combines synchronous HTTP calls with asynchronous Kafka event-driven processing and a reliability guarantee via the Outbox Pattern.

sequenceDiagram autonumber participant C as 🌐 Client participant OS as 📦 Order Service participant ODB as 🗄️ order_db participant IS as 📋 Inventory Service participant IDB as 🗄️ inventory_db participant K as 📡 Kafka participant PS as 💳 Payment Service participant PDB as 🗄️ payment_db Note over C,PDB: Phase 1 — Order Placement (Synchronous) C->>+OS: POST /api/order (OrderRequest) OS->>OS: Generate UUID orderNumber OS->>OS: Map OrderRequest → Order + OrderLineItems OS->>OS: Calculate totalAmount from line items OS->>ODB: Save Order + OrderLineItems (JPA @Transactional) ODB-->>OS: ✅ Persisted Note over C,PDB: Phase 2 — Event Publishing (Async + Retry) OS->>OS: Build OrderPlaceEvent from saved Order OS->>+K: kafkaTemplate.send("notificationTopic", event) K-->>-OS: ✅ Acknowledged alt Kafka publish fails (after 3 retries) OS->>ODB: Save to OutBox table (PENDING) Note over OS,ODB: Outbox Relay Worker picks up later end OS-->>-C: 201 "Order Placed Successfully" Note over C,PDB: Phase 3 — Payment Processing (Async / Event-Driven) K->>+PS: OrderEventConsumer receives OrderPlaceEvent PS->>PS: processPayment(event) PS->>PDB: Save Payment (PENDING → COMPLETED/FAILED) PDB-->>PS: ✅ Persisted PS-->>-K: Acknowledge message

Step-by-Step Data Flow

StepComponentActionData Involved
1 Client → Order Service POST /api/order OrderRequest{customerId, orderLineItemsDtoList[{skuCode, price, quantity}]}
2 Order Service Generate unique orderNumber (UUID) —
3 Order Service Map DTOs → JPA entities Order{orderNumber, customerId, totalAmount}, OrderLineItems{skuCode, price, quantity}
4 Order Service → order_db Persist order within @Transactional orders + order_line_items tables
5 Order Service Build Kafka event OrderPlaceEvent{orderNumber, customerId, totalAmount, orderTime, items[]}
6 Order Service → Kafka Publish to notificationTopic with retry (3 attempts, 2s backoff × 2 multiplier) JSON-serialized OrderPlaceEvent
7 Kafka → Payment Service OrderEventConsumer receives event (payment-service-group) Deserialized OrderPlaceEvent
8 Payment Service → payment_db Create Payment record Payment{paymentId, orderNumber, customerId, amount, currency, paymentMethod, status}

4. Outbox Pattern — Reliability Guarantee

When Kafka is unavailable, the system falls back to the Transactional Outbox Pattern to ensure at-least-once delivery.

flowchart TD A["Order Service: placeOrder()"] --> B{"Kafka.send() succeeded?"} B -- "✅ Yes" --> C["Event delivered to notificationTopic"] B -- "❌ No after 3 retries" --> D["@Recover: Save to OutBox table PENDING"] D --> E["OutboxRelayWorker runs every 30s"] E --> F["Fetch PENDING events retryCount less than 5"] F --> G["Set status → PROCESSING"] G --> H{"Kafka.send() succeeded?"} H -- "✅ Yes" --> I["Set status → PUBLISH"] H -- "❌ No" --> J["Increment retryCount"] J --> K{"retryCount >= 5?"} K -- "Yes" --> L["Set status → FAILED Dead letter"] K -- "No" --> M["Set status → PENDING retry next cycle"] style A fill:#4a90d9,color:#fff style C fill:#27ae60,color:#fff style I fill:#27ae60,color:#fff style L fill:#e74c3c,color:#fff

10. Communication Patterns Summary

PatternSourceTargetMechanismUse Case
Sync REST Order Service Inventory Service HTTP via InventoryClient (Spring HTTP Interface) Stock check & reduction during order placement
Async Event Order Service Payment Service Kafka (notificationTopic) Trigger payment processing after order is placed
Async Event Payment Service Order Service (planned) Kafka (paymentTopic) Notify order status update after payment result
Fallback Order Service Outbox → Kafka Outbox Relay Worker (scheduled every 30s) Guaranteed delivery when Kafka is temporarily down
Auth Client User Service JWT Bearer Token Stateless authentication for protected endpoints
